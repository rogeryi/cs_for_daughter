## 和 agent 一起做出游戏之后，我更关心什么

当初给你设计 CS101 这门课时，我有两个目的：一是让你通过 Python 学习程序设计的基础知识，二是让你学会与 agent 协作。

从这段时间做游戏的过程看，第二个目标已经有了不错的进展。你能够描述自己想要的游戏，试玩，发现问题，再提出修改要求。从人物形象、对话形式，到背景音乐、招募过程和剧情节奏，你逐渐把一个想法推进成了可以运行的作品。这些都是实际的能力，不应该因为代码主要由 agent 完成，就被一笔抹去。

但第一个目标，目前的完成情况让我不满意。

这里的问题不是“你有没有亲手敲完所有代码”，而是：游戏越来越完整的时候，你对程序设计的理解，有没有一起成长？

## 这不只是你的问题，也是课程的问题

我在 agent 出现之前，有二十多年的编程经验。分析问题和需求、确定设计方向、识别系统约束、编码实现、测试和调试，这些能力都是在一次次实践中慢慢形成的。很多时候，正是因为自己写不出来、程序运行不对，才不得不停下来思考，最终弄懂了原来不理解的东西。

但你的学习环境已经不同了。

一道对初学者颇有难度的习题，对今天的 agent 来说，可能就是一句话的事情。过去，“完成习题”通常意味着学生至少经历了一部分思考和实现；现在，作业完成得很好，并不能直接说明学习者已经理解了它。

这门课程本身也是 agent 根据我的要求设计的。回头看，它仍然太接近传统的课程安排：讲知识点、布置习题，再通过完成习题来练习和检验掌握程度。虽然我们把“学会与 agent 协作”加入了目标，却没有充分重新设计：当 agent 能直接完成作业时，你究竟应该通过什么过程获得自己的能力。

所以，我不想把这个问题简单归结为你不够努力，或者用了太多 AI。课程和学习方式本身，也需要调整。

## 我并不希望你回到没有 agent 的时代

我不认为解决办法是禁用 agent，要求你重新走一遍我当年的路。

能够使用更好的工具，本来就是你的机会。没有必要为了证明自己在学习，刻意拒绝工具的帮助。与 agent 沟通需求、讨论方案、推动实现、检查结果，也应该成为你能力的一部分。

但我们需要分清两件事：**借助工具完成了一个作品，以及借助这个过程学会了什么。**

这两件事可以同时发生，却不会自动同时发生。如果每次遇到问题，都只是把现象告诉 agent，等待它修改，再确认“现在可以了”，你可能越来越擅长推动作品，却仍然不太清楚作品内部是怎样运转的。

我希望我们找到的，是一种既保留工具优势，又能让理解真正积累下来的学习方式。

## 先做出来，可以是学习的开始

一个值得尝试的办法，就是先让 agent 做出你感兴趣的东西，再围绕这个作品展开学习。

你喜欢游戏，那么角色、装备、对白、战斗和存档，就不再只是抽象的练习题。你可以追问：点下攻击按钮以后，程序依次做了什么？为什么获得一把剑，还不一定会提高攻击力？为什么读档不仅要恢复角色血量，还要恢复章节和队友？Grox 为什么在夜谈结束后才正式加入？

然后，把这些具体问题和你学过的变量、条件判断、循环、函数、类与对象联系起来。

不过，学习不能停在“让 agent 解释过了”。

主对话中，agent 已经给代码加了注释，也整理了代码与课时的对应关系。这一步有用，但它主要完成的是学习材料的准备。材料放在那里，不等于你已经理解；看解释时觉得顺畅，也不一定意味着离开解释之后，自己仍然能说清楚。

接下来更重要的是，在 agent 的帮助下，把这个游戏当作一个可以研究和实验的程序。让它带你找到一个具体功能的相关代码，解释各部分怎样连接，再一起观察程序实际运行时，内部究竟发生了什么。

例如，研究一次攻击时，不仅看屏幕上“敌人掉血了”，还可以请 agent 帮你设置断点、添加日志或显示关键变量，观察攻击前后的生命值、攻击力、防御力和护盾，跟踪程序调用了哪些函数、进入了哪个条件分支，以及这些数值是按什么顺序计算和修改的。这样，课堂上学过的变量、判断、函数和对象，就能与运行中的具体状态联系起来。

接着，可以和 agent 一起做一个局部修改：调整一个数值、改变一个判断条件，或者修改一小段计算规则，再运行一次，重新观察同样的内部状态。比较修改前后有哪些变化，沿着代码追问这些变化为什么发生。如果有看不懂或与预想不同的地方，就让 agent 帮你缩小观察范围、增加观察点，再做一次实验。

这个过程不要求你一开始就能独立读懂代码、找出修改位置，或者自己使用所有调试工具；这些都可以在 agent 的帮助下逐步学会。但你需要真正参与研究：看代码、看运行状态、提出问题，并把修改与结果之间的关系弄清楚。通过反复“研究代码—观察运行—局部修改—重新观察”，逐渐建立对程序如何工作的理解，比只读完一份解释或注释更有价值。

## 如果想把兴趣发展成专业，标准就需要不同

我也希望你借这个过程，进一步想清楚自己对游戏设计的兴趣，具体落在哪里。

你可能喜欢创造世界和人物，可能喜欢设计规则与玩家体验，也可能喜欢把这些想法变成稳定运行的软件。这些兴趣可以重合，但并不是同一件事。你不需要现在就决定未来，更不需要为了证明喜欢游戏，就假装喜欢其中的每一项工作。

但如果你确实希望往软件设计与开发的专业方向走，就需要逐渐用更专业的标准要求自己。

这里的“专业”，不是现在就要达到职业开发者的水平，也不是所有事情都必须独立完成，而是不能只满足于“它终于能跑了”。你需要逐步理解它为什么这样运行，能判断方案是否合适，知道修改会影响什么，能够检查 agent 给出的实现，并在结果不符合预期时，有依据地继续分析。

独立能力也不意味着不用工具，而是使用工具时，你有自己的问题、判断和验证依据。

我不希望把你对游戏的兴趣变成一份沉重的考核。恰恰因为你对它有兴趣，我才希望这个项目不只留下一个游戏，也能帮助你认识自己：你是否愿意理解背后的机制，是否享受把问题想清楚，是否愿意在作品“看起来已经完成”之后，再向里面多走一步。

你可以让 agent 帮你把游戏做出来。接下来，我更希望看到的是，你逐渐知道自己做出了什么，以及为什么它能够这样工作。

对于希望往专业方向发展的初学者来说，agent 的价值不仅在于它可以帮你把东西做出来，更在于它可以帮助你研究代码、观察运行、理解设计，并在不断实验中学习。**相比于学会让 agent 替你完成任务，学会借助 agent 研究和学习，是更重要的能力。**前者帮助你完成眼前的作品，后者帮助你把这个过程转化为属于自己的知识、理解和判断力。这也是我更希望你在后续学习中有意识去练习的事。
