# CS102 课程设计

---

## 设计背景

原始 CS102 定位为“C++ 面向对象编程与软件设计”，内容集中在 C++ 基础语法、类、对象、封装、继承、多态和简单控制台游戏。

新的课程目标更宽：未来不再单独开设完整的数据结构和操作系统课程，而是把这些课程中最有价值、最适合高中阶段的核心概念，嵌入 C/C++ 编程课程中。

因此，CS102 需要承担三个角色：

1. 从 Python 过渡到现代 C++
2. 建立内存、容器、线程、文件等系统直觉
3. 建立复杂软件设计和源码分析的入门能力

课程采用一对一现场授课。教师和学生围绕同一个 Xcode 工程进行结对编程，现场讲解、现场运行、现场调试、现场追问。课程设计重点不是让学生课后独立消化大量材料，而是在课堂中通过观察、操作和表达逐步形成理解。

---

## 核心设计判断

### 1. C++ 为主，C 为辅助

课程主语言使用 C++23。C++ 是未来学习图形学、游戏引擎、性能敏感软件的重要语言，也是理解大型开源项目的重要入口。

C 不作为完整独立课程，而是在以下场景中作为“底层透镜”出现：

- 指针和地址
- C 字符串与 `std::string` 对比
- 数组和连续内存
- 编译、链接、头文件
- 程序入口和简单系统调用概念
- Godot/游戏引擎常见的 C 风格接口边界
- 第三方库、ABI、GDExtension C API 的基础直觉

这样可以避免先完整学习 C 带来的过高挫败感，同时保留理解底层模型的价值。

### 2. Xcode IDE 工程是主教学环境

课程主环境使用 Xcode IDE 工程，而不是只使用命令行或单个 `.cpp` 文件。原因是 CS102 的重点之一是“看见程序如何运行”：

- 通过断点观察控制流
- 通过变量面板观察对象状态
- 通过单步执行理解函数调用
- 通过调用栈理解程序如何到达当前位置
- 通过线程视图理解并发程序的多条执行线
- 通过调试输出和 lldb 命令辅助理解地址、指针和生命周期
- 通过 Memory Graph、变量地址和对象成员排列观察内存布局
- 通过 lambda 捕获变量的调试视图理解闭包对象本质上也是对象

每次课程开始前，先创建本周目录，例如 `CS102/week03/`，再在目录中创建可用 Xcode 打开的空 C++ 工程。学生可以在 IDE 里编辑代码，也可以通过和 AI 对话生成代码，再把代码加入工程。运行、调试、观察都以 Xcode 为主。

命令行和 CMake 保留为辅助工具，用于理解开源项目、构建系统、跨平台 C++ 项目和编译产物。当需要观察目标文件、可执行文件、符号或链接过程时，由 AI 调用命令行并解释结果。

### 3. 一对一现场课优先互动和可观察性

每节课按“教师示范 -> 学生接手 -> 调试观察 -> 口头解释”的循环设计。

教师不只检查代码是否运行，还要持续追问：

- 这行代码改变了哪个变量？
- 这个对象现在由谁拥有？
- 调用栈为什么会到这里？
- 这个 vector 为什么扩容后地址变了？
- 这个 lambda 捕获的是值还是引用？
- 这个线程现在为什么在等待？

学生的理解标准不是“照着写完”，而是能在 Xcode 中指出现象，并用自己的话解释原因。

### 4. 标准库优先，而不是手写基础设施优先

课程不以手写链表、红黑树、哈希表作为主线。高中阶段更重要的是：

- 何时使用 `std::vector`
- 何时使用 `std::unordered_map`
- 为什么 `std::priority_queue` 适合任务调度和 A* 的开放集
- 为什么游戏开发中常常偏好连续内存
- 为什么生命周期和所有权会影响程序稳定性

学生应先获得“正确使用工具”的能力，再通过必要的内部机制解释建立理解。

### 5. 系统概念跟随语言机制出现

系统概念不独立成课，而是随编程问题自然出现：

| 编程机制 | 融入的系统概念 |
|---------|----------------|
| 指针、引用 | 地址、地址空间、对象位置 |
| 栈对象、堆对象 | 生命周期、作用域、所有权 |
| 头文件和源文件 | 编译、链接、翻译单元 |
| 文件读写 | 文件系统、路径、资源加载 |
| `std::thread` / `std::jthread` | 线程、进程、并发执行 |
| `mutex` / `condition_variable` | 数据竞争、同步、等待通知 |
| 容器和算法 | 数据结构、复杂度、缓存直觉 |
| Xcode 调试器 | 调用栈、线程状态、变量状态、运行时观察 |
| Xcode Memory Graph / lldb | 对象关系、指针指向、简单内存布局 |
| lambda 调试观察 | 闭包捕获、匿名函数对象、状态保存 |

### 6. 软件设计从“能维护”出发

课程不把软件设计变成抽象术语堆叠，而是围绕学生能观察到的痛点：

- 一个文件太长怎么办？
- 为什么有些类很难改？
- 为什么资源释放会出 bug？
- 为什么模块之间互相调用会混乱？
- 为什么游戏引擎要有 Node、SceneTree、Signal、Resource？

设计原则以实用为主：

- 单一职责
- 清晰接口
- 依赖方向
- 生命周期管理
- 事件解耦
- 数据和行为的合理边界

## 课程架构

### CS102A: 现代 C++ 编程与内存模型

上半部分解决“如何写现代 C++ 程序，以及程序在内存里如何存在”。

内容重点：

- 每周 Xcode IDE 工程、编译、运行、断点调试、命令行产物观察、CMake 辅助
- 类型、表达式、控制流、函数
- 值、引用、指针、`const`
- 地址、数组、栈、堆、生命周期
- `std::string`、`std::vector`、`std::array`、`std::span`
- 类、构造、析构、封装
- RAII、智能指针、错误处理
- 标准算法和 ranges
- 上半学期小项目

### CS102B: 标准库、并发与软件系统设计

下半部分解决“如何选择数据结构、如何处理并发、如何理解复杂软件结构”。

内容重点：

- 源码分析方法
- 标准库容器全景
- 树、哈希表、队列、优先队列的使用场景
- 复杂度和性能直觉
- 文件系统、资源加载、时间系统
- 线程、同步、线程安全队列
- 模块、接口、依赖方向
- Godot 核心设计案例
- mini scene tree / 小型 2D 框架项目

## 明确不做的事情

本课程不追求完整替代大学数据结构、操作系统、编译原理或软件工程课程。

暂不深入：

- 手写红黑树、B 树、完整哈希表
- 操作系统内核、调度器、虚拟内存实现
- 模板元编程、复杂 SFINAE、深度 concepts
- 协程作为主线内容
- 大规模编译或通读 Godot 源码
- C++ modules 作为课程核心要求

这些内容可以作为“知道它存在”的扩展，但不作为本课程成败标准。

## 期末能力画像

完成 CS102 后，学生应能做到：

1. 打开一个中型 C++ 项目，找到入口、模块边界和核心类型
2. 解释一个对象由谁创建、由谁拥有、何时销毁
3. 根据数据访问模式选择合适的标准库容器
4. 识别简单的数据竞争和生命周期风险
5. 读懂 Godot 一类项目中 Node/SceneTree/Signal/Resource 的设计意图
6. 实现一个小型但结构清晰的 C++ 项目，并写出源码分析报告
7. 能用 Xcode 调试器解释一次函数调用、一次对象状态变化和一次线程执行现象
